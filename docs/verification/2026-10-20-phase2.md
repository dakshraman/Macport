# Phase 2 verification — 2026-10-20

This record covers the Phase 2 runtime boundary and parity core after the
`core-runtime`, `qemu-control`, `tools-media`, `vm-host` and `ui-parity`
workstreams were merged into `main`.

It is deliberately a record of what was observed, not a claim that every guest
path was re-exercised. The unverified items are listed at the end.

| Double start | second `macportctl start "Host Test"` | refused: `already running (pid …)`; exactly one host process |
| App adoption | quit `Macport.app`, relaunch while host runs | host stayed alive; still one host; status still `running` |

Snapshot placement was checked with `qemu-img snapshot -l -U`:

- `disk.qcow2` carried the snapshot **and 81.8 MiB of VM state**;
- `efi-vars.qcow2` carried the same tag with **0 B** of VM state.

That is the intended split. The EFI varstore is snapshotted for boot-order
rollback, but the root disk is the explicit VM-state target.

## Defects found and fixed during the pass

### 1. Host never serviced valid control requests

The host blocked its main thread in `CFRunLoopRun`. The control server runs on its
own queue, so malformed requests were answered directly, but valid requests are
main-actor isolated and never ran: `macportctl status` timed out while the host
was healthy. The raw run loop does not drain the main dispatch queue.

**Fix:** `serve()` now suspends the async entry point on a
`CheckedContinuation`, and shutdown resumes it. The process stays alive with the
main queue serviced.

### 2. Snapshot state was written into the EFI varstore

HMP `savevm` chooses the first writable qcow2 device implicitly. With a writable
pflash varstore, that was `efi-vars.qcow2`; a 2 GiB guest's compressed state was
written into the 64 MiB NVRAM image. QEMU also refused the older raw varstore
outright: `Device 'pflash1' is writable but does not support snapshots`.

**Fix:** new and existing bundles convert the varstore to qcow2 on start; QEMU
uses explicit block-node names (`macport-root`, `macport-vars`); snapshots use
QMP `snapshot-save`/`snapshot-load`/`snapshot-delete` with `vmstate =
macport-root` and both writable nodes in `devices`. The old varstore remains
bootable and is converted, not discarded.

### 3. `macportctl stop` could leave a live host behind

A graceful guest stop can take longer than the default 10-second control timeout.
The CLI treated the timeout as fatal, exited before `shutdownHost`, and left a
host process with no guest. A later `start` was then refused.

**Fix:** `stop` uses a 25-second client, treats a failed stop request as
best-effort, always sends `shutdownHost`, and waits 20 seconds for the host to
exit before reporting failure. A live graceful stop now completes in about 11
seconds and leaves no process or `runtime.json`.

## Windows driver media

The QEMU engine builds a second USB CD-ROM from a `virtio-win` ISO when one is
present. The builder, the `DriverPaths` answer-file entries, the two-CD USB
topology and the missing-media warning are covered by unit tests. The UI now
shows a Problem card and the creation preflight lists the exact paths searched
when the ISO is absent.

**Not verified:** a live Windows install with Macport Tools. No `virtio-win.iso`
is present on this host, so `MacportTools.resolve()` returns `nil`. The install
remains a Windows 11 Setup boot; networking/display during a completed install
are unproven until a driver ISO is supplied.

## Not re-run in this pass

- Virtualization.framework Ubuntu boot after the runtime refactor.
- Windows 11 install/boot after the runtime refactor.
- QEMU windowed display (`-display cocoa`); the live pass used `-display none`.
- Bridged networking, vTPM, USB passthrough, shared folders for QEMU guests.

## Cleanup

The `Host Test` bundle was stopped, deleted with `--force`, and the app was
quit. No `MacportVMHost` or `qemu-system-aarch64` process was left running.
